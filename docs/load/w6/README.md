# W6 부하 측정 결과 (시뮬레이션)

위젯 방문자가 동시에 많아질 때 서버가 대화 첫 응답을 얼마나 빨리 내는지 k6로 쟀다. 모델 자리에는 목업 엔진을 두었으므로 모든 수치는 **시뮬레이션 기준**이다. 서버, Postgres(Docker), k6가 노트북 한 대(Apple M1 8코어, 16GB)에서 함께 돌았다. 실행일은 2026-11-11이고, 숫자는 이 폴더의 근거 파일에서 센 값이다.

**요약.**
- 동시 방문자 10~800명(초당 대화 1.5~124턴)에서 대화 첫 바이트 p95는 두 번의 측정 모두 20ms 아래였다(7.5~19.5ms).
- 1,200명(초당 약 183턴)에서는 서버의 이벤트 루프가 평균 90% 바빠졌고 p95가 89ms와 159ms로 올랐다. 이때 기기 전체 CPU는 57~62%였고 Postgres VM도 한도에 닿지 않았다. 한계는 Node 프로세스 하나다.
- 1,200명에서 서버 CPU의 30%는 응답 쓰기, 27%는 Prisma가 썼다.
- 잔액은 크레딧 원장 전체의 합계다. 그래서 원장이 10만 행이면 첫 바이트 p50이 21ms, 30만 행이면 52ms 늘었다(400명 기준).
- 측정한 대화 72,935턴에서 실패는 0건이었다.

## 무엇을 쟀나

- **방문 한 번.** k6 가상 방문자 한 명이 위젯이 보내는 요청을 차례로 보낸다. 대화창 문서, 정적 파일 두 개(`app.js`·`app.css`, 동시에), 인사말, 위젯 열림 사건을 받은 뒤 질문 2개를 보내고 떠난다. 첫 질문 사건은 위젯처럼 응답을 기다리지 않고 질문과 겹쳐 보낸다. 질문 사이 생각 시간은 평균 3초다. 사람보다 짧게 잡아 방문자 한 명이 내는 부하를 키웠다. 질문 5개 중 1개는 상담원 연결 기록까지 쓴다.
- **측정 서버.** 운영과 같은 `createApp` 조립에서 엔진만 목업으로 바꿨다. 목업은 첫 조각을 바로 내고 이후 글자마다 20ms를 쉰다. 그래서 응답 첫 바이트까지가 서버 몫이다(테넌트·잔액·이전 대화·지식 조회, 모더레이션). 대화·위젯 사건의 IP당 요율 제한은 미들웨어를 그대로 지나가되 상한에 닿지 않게 올렸다. k6가 127.0.0.1 한 곳에서 방문자 전부를 흉내 내기 때문이다. 콘솔, 결제, Sentry는 껐다.
- **지표.**
  - 대화 첫 바이트는 k6가 잰 `POST /api/chat` 응답의 첫 바이트 시간이다. 서버는 첫 조각을 받은 뒤에야 SSE 헤더를 보내므로 첫 조각 시간과 같다.
  - 서버 기록 TTFT는 서버가 대화 요청 사건에 적은 첫 조각 시간이다. 콘솔 지표와 같은 값이고 같은 nearest-rank로 셌다. 이 기록을 잴 때 실행기는 셀 구간을 k6를 띄운 시각에서 잡았다. 그래서 k6가 시작하기까지 걸린 시간만큼 k6의 유지 구간보다 앞섰고, 표본 수가 단계마다 몇 개 다르다(800명 A 7,429 대 7,421). 그 뒤 실행기는 k6 `setup()`이 남긴 시작 시각으로 구간을 잡게 고쳤다.
  - 루프 사용률(ELU)은 Node 이벤트 루프가 일한 시간의 비율이다. 1에 가까우면 요청이 루프 차례를 기다린다.
  - 기기 CPU는 서버, k6, Docker VM(Postgres), Docker 백엔드(포트 프록시)의 CPU를 1초마다 잰 값이다. 프로세스별 값은 코어 하나 기준, 기기 전체는 모든 코어 기준이다.
- **사다리.** 동시 방문자 10, 50, 100, 200, 400, 800, 1,200명을 차례로 돌렸다. 단계마다 15초 동안 방문자를 늘리고 60초 동안 유지했다. 지표는 유지 구간에 시작한 요청만 셌다. 마지막에 10명 단계를 다시 돌려 앞 단계의 흔적이 남았는지 봤다. 같은 사다리를 두 번(A, B) 돌렸다.
- **단계마다 새 테넌트.** 잔액이 원장 합계라서, 앞 단계가 쌓은 원장 행이 뒤 단계의 잔액 조회를 무겁게 한다. 단계마다 데모와 같은 FAQ를 가진 새 테넌트를 썼다. 원장 크기의 영향은 따로 쟀다.

## 1,200명에서 막히는 곳은 Node 프로세스 하나다

| 동시 방문자 | 서버 | k6 | Docker VM(Postgres) | Docker 백엔드 | 기기 전체 |
| --- | --- | --- | --- | --- | --- |
| 400 | 38.5 | 18.3 | 73 | 14.5 | 25.8 |
| 800 | 61.2 | 30.8 | 139.7 | 27.5 | 42 |
| 1,200 | 92.9 | 45.8 | 207.8 | 39.9 | 57.2 |

사다리 A의 유지 구간 평균이다. 기기 전체는 모든 코어 기준 %, 나머지는 코어 하나 기준 %다.

- 800명에서 1,200명으로 가면 루프 사용률이 0.56~0.58에서 0.90으로 오른다. 루프가 쉬는 시간이 거의 없어지면 새 요청은 앞 일이 끝나기를 줄 서서 기다린다. 그래서 p95가 11~13ms에서 89~159ms로 뛴다.
- 한 번의 긴 멈춤은 아니다. 1,200명에서도 루프 지연 p99의 최대는 16~20ms였다. 요청 하나가 첫 바이트까지 루프 차례를 여러 번 기다리고(DB 조회 3~4번이 돌아올 때마다), 그 기다림이 쌓인 값으로 보인다.
- 이때 서버 프로세스는 코어 하나의 93%를 썼고, 기기 전체(성능 코어 4개와 효율 코어 4개)는 57%였다. 다른 코어가 쉬어도 이벤트 루프는 스레드 하나에서 돈다. 다만 기기가 57%면 성능 코어는 더 바빴을 수 있다.
- Postgres는 코어 2개쯤, k6는 코어 절반쯤을 썼다. Docker VM에는 vCPU 8개가 있고(`docker info`), 원장 30만 행 실험에서는 VM이 평균 377%까지 썼다. 그러니 1,200명의 208%는 DB 쪽 한도가 아니다.
- 두 사다리의 1,200명 단계에서 GC는 초당 15ms 안팎이었고 한 번에 6ms를 넘지 않았다. 지연은 GC가 아니라 일로 꽉 찬 루프에서 온다.
- 1,200명은 두 번의 p95가 89ms와 159ms로 크게 달랐다. 루프가 90% 바쁠 때는 짧은 흔들림도 줄을 길게 만들어서, 포화 근처의 백분위는 회차마다 흔들린다.

**서버 CPU를 어디에 쓰나.** 1,200명을 한 번 더 돌리며 `node --cpu-prof`로 프로파일을 떴다. 프로파일러 비용이 들어가 이 실행의 p95는 143.6ms였다. 바쁜 시간 69.2초를 패키지와 영역별 자체 시간으로 묶었다([profile/profile.md](profile/profile.md), `load/profile.ts`).

| 묶음 | 바쁜 시간 중 % | 들어간 것 |
| --- | --- | --- |
| 소켓 쓰기·HTTP 응답 | 30.0 | `writev`, Node streams, `_http_outgoing`, `stream_base_commons`, `net`, `buffer`, `utf8Slice` |
| Prisma | 27.1 | `@prisma/client`, wasm(Prisma 7 쿼리 컴파일러), `@prisma/adapter-pg` 등 |
| 목업 엔진의 타이머 | 7.7 | `engine/mock`, timers, `timers/promises`, `event_target`, `abort_controller` |
| node-postgres | 7.2 | `pg`, `postgres-array`, `pg-protocol`, `pg-pool`, `pg-types` |
| 이 레포의 앱 코드 | 4.5 | `apps/server/src`, `packages/contracts` |
| Express·요율 제한·zod | 2.8 | `express`, `router`, `send`, `http-errors`, `express-rate-limit`, `body-parser`, `raw-body`, `serve-static`, `path-to-regexp`, `zod` |
| GC | 2.1 | |
| 그 밖 | 18.5 | 비동기 처리(`runMicrotasks` 3.9), 엔진 내부(`(program)` 3.6) 등 |

- 응답 쓰기가 가장 크다. 목업은 글자마다 SSE 이벤트 하나를 쓰므로 답 하나에 소켓 쓰기가 100번 넘게 일어난다. 쓰기를 모아 보내면 줄일 수 있다.
- 그다음이 DB 접근이다. 대화 턴마다 테넌트, 잔액, 이전 대화(두 번째 질문부터), 지식 27개를 읽고, 턴 저장 트랜잭션과 사건 한 건을 쓴다. 방문마다 문서·인사말·사건이 테넌트를 다시 읽는다. 바뀌지 않는 테넌트와 지식을 캐시하면 쿼리가 준다.
- 목업 엔진 몫(7.7%)은 실제 엔진에서는 상류 SSE를 해석하는 비용으로 바뀐다.

## 원장이 길수록 대화마다 느려진다

잔액은 크레딧 원장의 합계(`sum(delta)`)이고 대화 턴마다 한 번 조회한다. [ADR-0007](../../adr/0007-credits-and-payment-idempotency.md)은 "내역이 쌓일수록 잔액을 더하는 시간이 늘어남"을 받아들인 대가로 적었다. 이 측정은 그 대가의 크기다. 동시 방문자 400명에서 단계 테넌트의 원장에 차감 기록을 미리 넣고 쟀다.

| 단계 시작 원장 행 | 잔액 조회 한 번 (부하 없을 때) | 첫 바이트 p50 / p95 / p99 (ms) | 서버 기록 TTFT p50 / p95 (ms) | Docker VM(Postgres) CPU % |
| --- | --- | --- | --- | --- |
| 1 | 1.3~1.7ms (4,547행) | 4.2 / 8.1 / 13.6 | 4 / 7 | 73 |
| 100,001 | 15~17ms (104,547행) | 24.9 / 39 / 87.4 | 24 / 38 | 201 |
| 300,001 | 27ms (304,517행, 병렬 스캔 3개) | 56.3 / 159.1 / 260.4 | 56 / 158 | 377 |

- 초당 대화 턴은 세 경우 모두 약 61턴으로 같았다. 같은 일을 하는데 Postgres CPU가 2.8배, 5.2배로 늘었다. 턴마다 그 테넌트의 원장 전체를 다시 더하기 때문이다.
- 서버 쪽도 30만 행에서 CPU가 40%에서 55%로, 루프 사용률이 0.38에서 0.51로 올랐다. 응답을 기다리며 열려 있는 요청이 늘어난 몫으로 보이지만 원인은 확인하지 않았다.
- 잔액 조회 한 번은 측정이 끝난 뒤 부하 없는 DB에서 따로 쟀다([balance-query.txt](balance-query.txt)). 30만 행에서 Postgres는 혼자일 때 병렬 작업자 3개로 27ms에 끝냈다. 부하 중에는 다른 조회와 CPU를 나눠 써서 첫 바이트가 52ms 늘었다.
- 답이 있는 턴마다 원장이 한 행 는다. 하루 1,000턴을 답하는 테넌트는 약 100일 뒤 10만 행, 약 300일 뒤 30만 행이 된다.
- 고치는 방향은 잔액 스냅샷이다(README '다음 확장'). 결제·크레딧 코드라 사람이 결정한다.

## 시나리오를 고친 뒤 다시 쟀다

처음 측정한 뒤 다른 에이전트의 주석 검토가 시나리오와 위젯의 차이 둘을 짚었다. 대화창 정적 파일 두 개를 받지 않았고, 첫 질문 사건을 질문 앞에 차례로 보냈다. 실제로는 서버가 정적 파일을 `max-age=0`으로 보내서 브라우저가 열 때마다 다시 받거나 재검증하고, 위젯은 사건을 기다리지 않고 질문을 보낸다. 둘을 고치고 처음부터 다시 쟀다. 위 표는 모두 고친 시나리오의 값이다.

| | 800명 서버 CPU % | 800명 루프 사용률 | 1,200명 서버 CPU % | 1,200명 루프 사용률 |
| --- | --- | --- | --- | --- |
| 고치기 전 (A / B) | 53.4 / 54.3 | 0.52 / 0.52 | 84.4 / 83.1 | 0.83 / 0.82 |
| 고친 뒤 (A / B) | 61.1 / 59.1 | 0.58 / 0.56 | 92.9 / 92.4 | 0.90 / 0.90 |

같은 방문자 수에서 서버 CPU가 5~9%p 올랐다. 차이는 대부분 방문마다 받는 정적 파일 두 개(약 18KB)로 보인다. 정적 파일을 CDN에서 내보내면 이만큼이 Node에서 빠진다. 고치기 전 기록은 [old-ladder-a](old-ladder-a/report.md), [old-ladder-b](old-ladder-b/report.md)에 있다.

## 실제 서비스로 옮겨 읽기

- **옮겨 쓸 숫자는 초당 대화 턴이다.** 동시 방문자 수는 생각 시간에 달렸다. 이 측정의 방문자는 3초마다 묻는다. 실제 방문자는 더 오래 생각하므로, 같은 턴 수면 동시 방문자는 훨씬 많다. 이 기기에서는 초당 약 120턴까지 p95가 20ms 안이었고, 약 180턴에서 루프가 찼다.
- **방문자가 느끼는 첫 글자 시간은 모델 몫이 대부분이다.** 여기의 서버 몫(400명 p50 4ms, p95 8ms)에 W5에서 잰 모델 몫(Sonnet 5.5 TTFT p50 1,123ms, p95 1,544ms)이 더해진다. W5 값은 서버 안에서 잰 것이라 HTTP 왕복은 빠져 있다.
- **실제 엔진은 스트림 하나에 드는 CPU가 다르다.** 목업은 글자마다 쓰고 상류를 읽지 않는다. 실제 엔진은 여러 글자를 한 조각으로 받지만 상류 SSE를 해석하고 필터(도구 태그, 되풀이 문장)를 거친다. 그래서 루프가 차는 지점은 목업 기준이다.
- **더 받으려면 프로세스를 늘린다.** 지금은 요율 제한 카운터와 무작위로 만든 비밀값이 프로세스 메모리에 있어서 서버를 여러 개 띄우면 깨진다(README '배포 전 할 일'). 응답 쓰기와 DB 쿼리를 줄이는 것은 그 전에 할 수 있는 일이다.

## 한계

- 모델이 없다. 목업은 첫 조각을 바로 내고 글자마다 20ms를 쉰다.
- 서버, Postgres, k6가 기기 하나(M1, 성능 코어 4개와 효율 코어 4개)의 CPU를 나눠 쓴다. Postgres는 Docker VM 안에 있고 연결은 Docker Desktop의 포트 프록시를 거친다.
- 동시 방문자 수를 고정하는 닫힌 모델이다. 서버가 느려지면 방문자도 덜 묻는다. 그래서 포화 근처의 지연은 도착이 일정한 실제 트래픽보다 낮게 잡힐 수 있다.
- 사다리는 두 번, 단계마다 60초다. 1,200명은 회차 차이가 크다.
- 방문자는 매번 새 방문자(정적 파일을 캐시 없이 받음)이고 질문 2개를 묻는다. 생각 시간은 사람보다 짧다.
- 요율 제한 상한, 콘솔, 결제, Sentry는 운영과 다르게 두었다.
- 10명일 때 중앙값이 400명보다 높은 현상의 원인은 확인하지 않았다.
