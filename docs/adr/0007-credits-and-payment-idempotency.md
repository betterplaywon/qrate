# ADR-0007: 크레딧 과금 — 턴당 차감, 테넌트 범위 멱등 키, 결제 제공자 경계

- 상태: accepted (2026-11-06)
- 날짜: 2026-11-05
- 작성: 강지원

## 맥락

운영자는 "쓴 만큼 내는" 과금을 원한다(README 페르소나). 모델 호출 비용은 토큰에 비례하지만 운영자가 이해하는 단위는 "답변 몇 번"이다.
돈이 움직이는 경로는 둘이다 — 충전(결제 제공자의 승인·웹훅)과 차감(답변이 끝난 턴). 둘 다 네트워크 재시도로 같은 요청이 두 번
도착할 수 있고, 웹훅은 적어도 한 번 배달이라 중복·순서 뒤바뀜·위조를 전제해야 한다. 정의서의 성공 지표는 "중복 요청 재현 테스트 통과"다.

W4 결정(2026-11-05) 다섯 가지 중 이 ADR은 ①결제 제공자 ②멱등 키 ③크레딧 모델을 다룬다. ④이벤트 로그 ⑤A/B는 ADR-0008.

### 2. 멱등 키

| 항목 | 선택 | 버린 것 |
| --- | --- | --- |
| 범위 | `@@unique([tenantId, idempotencyKey])` | 전역 unique(W1 초안) — 클라이언트가 만든 키가 테넌트 간 충돌 |
| 출처 | 둘, 접두사로 구분(`turn:`·`topup:`·`seed:`·`adj:`) | 하나만 |
| 중복 응답 | 첫 번째와 같은 응답. 원장 추가는 기존 항목을 돌려준다. 충전 요청 재요청(같은 `Idempotency-Key`)은 첫 요청과 같은 201과 같은 본문(만든 직후의 주문)에 `Idempotent-Replayed: true`를 붙인다. 웹훅 재배달은 처음 판정(outcome)을 돌려준다 | 409, 재요청에 주문의 현재 상태 |
| 넣는 방법 | `INSERT … ON CONFLICT DO NOTHING`(createMany skipDuplicates) 뒤 그 키로 다시 읽기 | 먼저 조회 후 삽입(경쟁 조건), 예외 잡기 |

### 3. 크레딧 모델

| 항목 | 선택 | 버린 것 |
| --- | --- | --- |
| 차감 단위 | 답이 끝난 턴당 1 | 토큰 비례 요율 |
| 잔액 0 | 모델을 부르기 전에 402 `insufficient_credits`(위젯: 운영자에게 알려 달라) | 마이너스 허용(후불) |
| 잔액 | 원장 합계(SUM delta) | 테넌트에 잔액 열 캐시 |
| 차감 시점 | 턴 저장과 같은 트랜잭션(`appendTurn`의 `charge`) | 답 전송 전 선차감, 따로 차감 |
| 초기 크레딧 | 시드로 한 번 지급(`seed:initial`) | 0에서 충전만 |

## 결정

### 멱등 키

동일 요청 발생 시, 먼저 들어온 하나의 요청만 테이블에 추가하고, DB룰로 동일 요청에 대한 방어 진행 후 DB를 읽어 멱등한 응답을 전달해. 예기치 못한 추가 결제나 다른 응답을 받지 않을 수 있다는 것이 장점.

이름표 중복을 방지해야 하는 이유는 중복 요청이 가능하기 때문이다.
테넌트 범위가 회사 안이라면 다른 회사의 같은 이름표는 서로 다른 요청으로 보고 모두 수용한다.
그러나 범위가 전체라고 한다면 하나의 이름표만 허용 시, B사의 요청이 A사의 요청에 막히게 된다.
결론적으로, 테넌트 범위는 회사 안으로 한정하는 것이 현 서비스 방향과 부합하다.

### 결제 알림의 상태 전이

결제대기->실패->결제완료로 만든 것은 돈은 나갔지만 크레딧이 없는 경우를 방지하기 위해서다.
알림이 어떤 순서로 오더라도 끝 상태가 같도록 처리하기 위함이다.
그래서 결제대기->실패->결제완료 순서를 만들었다.

### 크레딧 모델

- 답변 한 번에 1크레딧 소모. 토큰에 맞춰 받으면 공정하지만 가격 산정 복잡도 증가. 고도화 시 추가 고려가 필요하다.
- 잔액이 0 이하라면 답변 모델을 호출하기 전에 402 응답을 전달해 답변을 하지 않는다. 모델을 부르지 않으니 비용이 들지 않는다.
- 크레딧은 답변 이후 차감한다. 미리 차감한다면 모델 실패나 사용자 화면 이탈 시, 다시 크레딧을 복구하는 로직이 요구되어지는데 답변 이후 차감하면 문제가 발생하지 않는다.
- 대화 저장과 크레딧 차감을 한 트랜잭션으로 묶어 무료로 답변을 제공하거나 고객사의 크레딧만 빠지는 경우를 방지했다.
- 잔액은 입출금 내역을 기준으로 판단. 잔액 칸을 따로 두지 않아 내역과 잔액이 어긋날 일이 없다.

### 결제 제공자

비즈니스를 목표로 만든 것이 아니기도 했고, 실 PG 어댑터를 부착하기 위해선 사업자 등록 등의 과정을 거쳐야 하기에 번거로움으로 와닿았다.
결제 알림 처리의 정확성을 파악하고자 이번 구현을 했음.
나중에 실제 PG를 부착할 수 있도록 구조를 만들어뒀음.
모의 PG로 우선 진행하고자함.

## 스스로 답해볼 유도 질문

1. 멱등 키의 유일 제약이 "조회 후 삽입"보다 안전한 이유는? 두 요청이 같은 밀리초에 들어오면 각각에서 무슨 일이 생기나?
2. 차감을 턴 저장과 같은 트랜잭션에 넣었다. 트랜잭션이 없다면 어떤 두 가지 불일치가 생길 수 있나? 지금 구조에서 "턴은 두 번 저장됐는데 차감은 한 번"은 왜 괜찮은가?
3. 잔액 확인은 모델 호출 전, 차감은 답이 끝난 뒤다. 그 사이에 같은 테넌트의 턴이 또 들어오면 잔액이 음수가 될 수 있다. 막으려면 무엇이 필요하고, 왜 지금은 받아들였나(ADR-0006 동시 턴 신호와 연결)?
4. 402를 모델 호출 전에 내는 것이 비용에 어떤 의미인가? 위젯이 이 상태를 "다시 보내기" 없이 보여 주는 이유는?
5. 웹훅이 두 번 오면 원장이 왜 두 번 움직이지 않는가? 순서가 뒤바뀌어 오면(승인 뒤 취소가 먼저) 무엇이 깨질 수 있고 충전 요청의 상태 전이로 어떻게 막나?
6. 토스페이먼츠 승인 API의 `Idempotency-Key`와 우리 원장의 멱등 키는 역할이 어떻게 다른가? 둘 다 필요한 이유는?
7. 원장 합계를 매번 계산하는 비용은 언제 문제가 되는가? 잔액 열을 두면 무엇을 새로 지켜야 하나?

## 트레이드오프

### 멱등 키·결제 알림의 상태 전이

- DB를 사용하지 않는 메모리 저장소 환경이라면, 메모리 저장소도 동일 동작할 수 있게 따로 세팅해야한다.
- 기존 화면이 아닌 새로고침이나 뒤로가기 후 결제 페이지에 재진입하여 재요청 시 결제 대기가 남을 수 있다는 단점이 존재한다.
- 지금 단계에서는 결제 완료 뒤에는 상태가 되돌아가지 않기에 결제 취소나 환불은 불가하다. 대신 추가 개발로 해결 가능.

### 크레딧 모델

- 짧은 답과 긴 답에 대한 소모 크레딧이 동일하기에 개발사(나)의 비용과 상당히 다를 수 있음.
- 내역이 쌓일수록 잔액을 더하는 시간이 늘어남.
- 잔액 확인과 크레딧 차감 사이에 추가 메시지가 온다면 크레딧이 음수 값으로 내려갈 수 있다. 음수값 증가를 막기 위해 크레딧이 음수가 된 뒤부턴 다음 질문부터 402로 모델을 동작시키지 않고 답변을 멈춘다. 완전히 막으려면 질문을 시작할 때 크레딧을 미리 예약하는 장치가 필요해 복잡해지고, 새는 양은 동시에 진행 중인 대화 수만큼으로 작아서 받아들였다.

### 결제 제공자

- 실제 PG 경험의 부재.
- 결제창 허용과 같은 부수작업이 남았음.

## 결과 확인 방법

- 저장소 계약 테스트: 같은 키 두 번 → 한 줄, 턴 차감은 턴 저장과 함께, 거절 턴은 0(`apps/server/test/repo-contract.ts`). Postgres 전용: 같은 키 동시 5회 → 한 줄, 시드 지급은 한 번(`repo-postgres.test.ts`).
- 유스케이스·HTTP: 잔액 0이면 엔진을 부르지 않고 402, 답이 있는 턴만 -1(`chat-service.test.ts`, `chat.test.ts`).
- 위젯: 402의 안내 문구와 버튼 없음(`packages/widget/test/turn.test.ts`), 콘솔 E2E의 잔액 100 → 98.
- 결제 멱등(모의 제공자): 웹훅 재배달·순서 뒤바뀜·위조와 콘솔 충전 요청 재시도를 테스트로 재현하고, 어느 경우에도 원장 한 줄을 확인한다.
  - 판정·전이: 상태 전이 표 6칸, 이벤트 순열 전부(이벤트 4개면 24가지)가 같은 끝 상태와 원장 최대 한 줄로 수렴(`apps/server/test/billing-settlement.test.ts`).
  - 저장소 계약: 같은 요청 키 → 같은 주문, 같은 이벤트 재배달 → 처음 판정 그대로·원장 그대로, 다른 이벤트 id의 같은 결과 → stale,
    실패 뒤 결제 완료 → 충전, 결제 완료 뒤 실패 → stale(`repo-contract.ts`). Postgres 전용: 같은 이벤트·다른 이벤트·결과 섞임·같은 요청 키를
    다섯 개씩 동시에 → 원장 한 줄, 주문 하나(`repo-postgres.test.ts`).
  - 서명: 금액 변조·다른 비밀·±301초·헤더 형식 → 거절, 서명이 맞아도 본문 모양이 다르면 거절(`billing-mock.test.ts`).
  - HTTP: 충전 재요청 201 + `Idempotent-Replayed`, 같은 키·다른 상품 422, 웹훅 재전송 200 + 헤더, 위조 401, 깨진 본문 400,
    제공자 없음 503·404(`billing-api.test.ts`).
  - 콘솔 E2E: 첫 충전 요청의 응답을 끊고 다시 눌러도 주문 하나, 결제 성공 +100 뒤 재배달·늦은 실패·웹훅 원문 재전송·위조에도 잔액 그대로
    (`apps/console/e2e/console.spec.ts`).
- 결제 멱등(토스페이먼츠 테스트 모드): 실제 토스 대신 가짜 토스를 fetch 자리에 꽂아 재현한다. 가짜는 실측한 토스를 따른다
  (같은 멱등 키는 오류 응답도 재생, 처리 중인 같은 키는 409이고 저장하지 않음, 모르는 결제 키는 조회 404 NOT_FOUND_PAYMENT·승인 404 NOT_FOUND_PAYMENT_SESSION).
  - 판정: 토스 상태 8개 → 결제 완료·실패·아직·범위 밖 표, 조회 404 NOT_FOUND_PAYMENT·NOT_FOUND만 "없음"이고 나머지 실패는 "묻지 못함",
    승인은 처리됐는데 답이 오류·409·500·끊김이어도 조회로 판정해 충전, 같은 결제의 재확정은 같은 멱등 키(`apps/server/test/billing-toss.test.ts`).
  - HTTP: 승인 성공 → 원장 한 줄, 재확정 → replayed, 돌아온 금액 불일치 → 422·토스 호출 0, 다른 주문의 결제 키 → 422, 조회도 실패 → 대기 뒤 같은 요청으로 회복,
    승인 답이 입금 대기처럼 끝나지 않은 결제 → 대기, 토스가 끝낸 뒤 재확정 → 조회로 충전, 확정·웹훅 본문의 결제 키 `.`·`..`(웹훅은 짝 없는 서로게이트도) → 400·토스 호출 0,
