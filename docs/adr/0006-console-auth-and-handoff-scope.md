# ADR-0006: 운영 콘솔 — 테넌트 키 인증, 같은 오리진 서빙, 핸드오프 범위

- 상태: proposed → 본인이 결정 이유·트레이드오프를 채운 뒤 accepted로 변경할 것
- 날짜: 2026-11-04
- 작성: 강지원

## 맥락

위젯은 방문자가 쓰고, 콘솔은 운영자(테넌트)가 쓴다. 콘솔은 그 테넌트의 대화 전부와 상담원 연결 요청을 보여 주므로
"누가 어느 테넌트를 보는가"를 서버가 비밀로 확인해야 한다. 위젯의 `data-tenant` 키는 설치 스니펫에 들어가는 공개 식별자라
인증이 아니다. 동시에 "상담원 연결"이 실제로 무엇을 하는지(운영자의 답이 위젯 안으로 돌아가는지, 밖으로 나가는지)에 따라
위젯·서버·콘솔의 범위가 크게 달라진다. 네 가지를 한 번에 정했다(설명 노트 참고).

1. 운영자 인증 — 자격 증명과 세션
2. 콘솔의 위치 — 콘솔 페이지와 API의 오리진
3. 핸드오프 범위 — 큐 + 상태 + 연락처 / 운영자 실시간 답장 / 알림
4. 미응답 큐의 정의 — 큐에 무엇이 들어가는가

## 고려한 대안

### 1. 운영자 인증

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. 테넌트 콘솔 키 + 서명된 HttpOnly 쿠키 (선택) | 인증 단위가 테넌트라 공개 키(`apiKey`)와 같은 행에 콘솔 키 해시 열(`consoleKeyHash`) 하나, 세션이 서명 JWT라 세션 테이블이 없고 서버가 여럿이어도 비밀만 같으면 검증, 가입·초대·재설정 흐름이 없어 코드가 작음 | 누가 처리했는지 남지 않음(운영자 표 없음), 한 테넌트의 운영자가 키 하나를 나눠 씀, 키 교체·회수는 플랫폼 운영자가 CLI로 함(`console-key:issue`·`console-key:revoke`, 다시 발급하면 기존 세션이 끊김) |
| B. 운영자 계정(이메일 + 비밀번호) | 운영자마다 계정이라 누가 처리했는지 남기고 한 사람만 막을 수 있음, 키를 나눠 쓰지 않음 | 가입·초대·비밀번호 재설정 흐름이 생김(재설정은 메일로 보내는 일회용·만료 토큰), 메일 발송 수단이 필요, 비밀번호 저장(느린 해시)·계정 존재 노출·무차별 대입을 지켜야 함 |
| C. 외부 로그인(매직 링크·OAuth) | 비밀번호를 저장하지 않음, 사람 단위 계정이라 처리자를 남길 수 있음 | 로컬 데모·E2E가 외부 서비스에 기댐(OAuth는 제공자에 클라이언트·리디렉트 URI를 먼저 등록, 매직 링크는 메일 발송) |

세션: 쿠키(`HttpOnly; SameSite=Strict; Path=/api/console`, https면 `Secure`)를 골랐다. 헤더 토큰(스크립트가 읽는 저장소)과의 차이,
CSRF를 왜 Origin 검사(대화 API와 같은 미들웨어)로 막는지를 적을 것.

### 2. 콘솔의 위치

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. 같은 서버가 `/console/`(정적)과 `/api/console/*`를 서빙 (선택) | 같은 오리진이라 CORS 헤더 없이 `SameSite=Strict` 쿠키가 그대로 실림, 서버 이미지 하나로 배포(Dockerfile이 콘솔 빌드를 함께 담음), 대화창 자산(`/frame/app.js`)과 같은 `express.static` 서빙 | 서버 이미지에 콘솔이 들어 있어 콘솔 화면만 고쳐도 서버를 다시 빌드·배포 |
| B. 별도 오리진(정적 호스팅·CDN) + CORS | 콘솔을 서버와 따로 빌드·배포, 정적 호스팅·CDN 캐시를 그대로 씀 | CORS 허용 목록과 credentials 설정이 필요(`Access-Control-Allow-Origin`에 `*` 불가, `Allow-Credentials: true`), 사이트가 다르면 쿠키에 `SameSite=None; Secure`가 필요하고 3자 쿠키 차단(Safari 기본)에 막힘, 상태를 바꾸는 요청의 Origin 검사가 콘솔 오리진도 받아야 함 |

개발 중에는 Vite dev 서버(5175)가 `/api`를 8787로 프록시하고 Origin 헤더를 서버 오리진으로 바꾼다 — 브라우저 입장에선 같은 오리진.

### 3. 핸드오프 범위

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. 큐 + 상태(열림·처리 중·완료) + 방문자 연락처 수집 (선택) | 새 실시간 채널 없이 기존 HTTP로 끝남(방문자 `POST /api/handoff`, 콘솔 목록·`PATCH`), 핸드오프 행으로 자동 해결률의 해결 여부를 가름(답 1개 이상·핸드오프 0) | 운영자 답이 위젯으로 돌아오지 않음(답은 이메일 등 밖에서), 방문자 화면은 "접수됐어요. 적어 주신 이메일로 답을 드릴게요"에서 끝남 |
| B. 운영자 실시간 답장(위젯이 운영자 메시지 수신, AI/사람 모드) | 방문자가 위젯 안에서 운영자 답을 바로 받음 | 서버에서 위젯으로 운영자 메시지를 보내는 채널이 새로 필요(지금 SSE는 질문 하나에 응답 하나), 대화마다 AI·사람 모드 상태와 운영자 부재 처리가 생김, W4~W6 일정과 겹침(README 계획의 결제·이벤트 로그·평가·부하) |
| C. A + 알림(이메일·슬랙 웹훅) | 운영자가 콘솔을 열어 두지 않아도 새 요청을 앎 | 고객사마다 외부 채널 설정이 필요(슬랙은 앱을 만들고 워크스페이스에 설치해 웹훅 URL을 받음, 메일은 발송 수단), 발송 실패를 재시도·기록해야 함(슬랙 웹훅도 `no_active_hooks` 같은 오류를 돌려줌) |

### 4. 미응답 큐의 정의

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. 핸드오프 행만(모델 신호 + 방문자 요청) (선택) | 이미 저장되는 `Handoff` 행(모델 신호·방문자 요청)을 그대로 씀, 큐의 뜻이 "사람이 봐야 한다고 표시된 것"으로 분명 | 모더레이션 차단(422)·엔진 오류로 답을 못 받은 방문자는 큐에 없음(그 턴은 대화에 저장되지 않음) |
| B. A + 정책 거절·오류 턴 | 답을 못 받은 방문자까지 운영자가 봄 | 차단·실패 턴은 지금 저장하지 않아 턴 저장 모양을 바꿔야 함, 욕설 차단(422)까지 큐에 들어와 처리할 요청이 묻힘 |
| C. A + 인용 0건 턴 | 도구 신호를 놓친 자료 밖 답도 후보로 잡음 | 자료 밖 질문에도 관련 자료 인용이 붙어 인용 0건으로 안 잡힘(시드 실측 2, 인용 2건), 인용이 필요 없는 답(인사·무관한 질문)과 인용만 빠진 자료 답(W5 2회차 Sonnet 2/36)이 섞임, 같은 값을 W5는 답 품질 결함("인용 빠짐")으로 셈 |

## 스스로 답해볼 유도 질문

1. 테넌트 키(`data-tenant`)는 공개인데 콘솔 키는 비밀이다. 둘을 같은 테이블의 두 열로 두는 것이 왜 괜찮은가? 콘솔 키가 새면 무엇이 노출되고, 교체는 어떻게 하나?
2. 콘솔 키를 sha256이 아니라 scrypt로 해시한 이유는? 사람이 정하는 키와 무작위 키에서 답이 달라지는가?
3. 세션을 DB 없이 서명 토큰으로 두면 "강제 로그아웃"은 어떻게 하나? 비밀을 바꾸면 어떤 일이 생기나?
4. `SameSite=Strict` 쿠키만으로 CSRF가 막히는가? 그런데도 login·logout·PATCH에 Origin 검사를 한 번 더 두는 이유는? GET에는 왜 두지 않았나?
5. 로그인 시도 제한을 IP당 고정 창으로 둔 것의 한계는? 서버가 둘 이상이면 무엇이 깨지나?
6. 큐의 상태 전이에 제한을 두지 않았다(완료 → 열림도 가능). 이 결정이 틀리는 경우는 언제인가?
7. 방문자 요청이 대화 없이 들어오면 빈 대화를 만든다. 이것이 "대화는 첫 턴 저장 때 생긴다"는 저장소 규칙과 어떻게 양립하나?
8. 실시간 답장(3-B)을 나중에 얹는다면 무엇이 그대로 남고 무엇이 바뀌나? 큐·상태·연락처 중 버려지는 것이 있나?

## 다시 검토할 신호

- (채워 넣기 — 힌트: 운영자가 둘 이상이 돼 "누가 처리했는지"가 필요해질 때, 테넌트가 늘어 키 공유가 문제될 때, 방문자가 "접수됐어요" 뒤에 이탈하는 비율)
- 같은 대화에 동시 턴이 오는 길이 생길 때(2026-11-04 판단: 지금은 위젯이 한 번에 한 턴만 보내고 대화 id가 탭마다 달라 미룸). 저장이 턴 단위라 질문·답이 섞이진 않지만 턴이 통째로 뒤바뀔 수 있고, 둘째 답이 첫째 질문을 모르는 것은 순서로 못 고친다 — 해법은 "진행 중 턴이 있으면 409"이고 서버가 여럿이면 공유 상태가 필요하다. 다시 보는 시점:
  - 대화 id를 브라우저에 보존해 탭 둘이 한 대화를 쓰게 될 때
  - 운영자 실시간 답장(핸드오프 B)으로 한 대화에 쓰는 주체가 둘이 될 때
  - W4 요율 제한·할당량을 붙일 때(같은 자리에 둔다)
  - W6 k6 시나리오를 짤 때(동시 세션은 서로 다른 대화 id, 같은 대화 동시 턴은 별도 케이스)

## 결과 확인 방법

- 계약 테스트: 로그인 실패는 이유를 가리지 않고 401, 세션 없음·위조·만료 401, 다른 오리진의 login·logout·PATCH 403, 시도 초과 429, 다른 테넌트의 대화·요청은 404(`apps/server/test/console-api.test.ts`, `console-session.test.ts`).
- 저장소 계약: 큐 목록·상태 전이·방문자 요청이 메모리·Postgres에서 같은 결과(`apps/server/test/repo-contract.ts`).
- 브라우저 E2E: 실제 Chromium이 HttpOnly 쿠키를 싣고 CSP 아래에서 콘솔이 도는지(`apps/console/e2e/console.spec.ts`).
