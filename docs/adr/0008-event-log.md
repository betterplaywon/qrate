# ADR-0008: 이벤트 로그 — 사건 등록표, 쓰기 통로, 콘솔 지표 정의

- 상태: proposed → 본인이 결정 이유·트레이드오프를 채운 뒤 accepted로 변경할 것
- 날짜: 2026-11-05
- 작성: 강지원

## 맥락

정의서의 성공 지표 중 둘이 이 PR의 대상이다. TTFT p50·p95는 "이벤트 로그 집계", 자동 해결률은 "핸드오프 없이 종료된 대화 비율(시나리오 기준 명시)"이다.
지금까지 TTFT는 `/api/chat` 요청마다 stdout에 찍히는 `chat_usage` JSON 한 줄에만 있었다. 그 줄은 프로세스 로그라 집계할 곳이 없고,
README에 적을 수치를 "어느 행에서 나왔는가"까지 따라갈 방법이 없었다. `Event` 표는 init 마이그레이션에 있었지만 어떤 코드도 쓰지 않았다.

사실의 주인은 이미 갈라져 있다. 핸드오프는 `Handoff` 표(모델 신호·방문자 요청 두 출처), 결제는 `PaymentEvent`·`CreditLedger`가 갖고 있다.
TTFT·실패·거절·위젯 열림만 어디에도 없었다. 실패·중단된 턴은 `appendTurn`에 닿지 않아 대화 표에 남지 않고, TTFT는 HTTP 계층만 안다.
저장소 구현이 둘(메모리·Postgres)이라 백분위 정의가 두 구현에서 같아야 한다. 위젯의 런처는 서버를 부르지 않으므로(ADR-0003) 열림을 아는 곳은
서버 오리진의 대화창 iframe뿐이고, 거기서 오는 공개 POST는 공개 키만 있으면 꾸밀 수 있다.

W4 결정(2026-11-05) 다섯 가지 중 ①~③은 ADR-0007이다. 이 ADR은 ④ 이벤트 로그를 다룬다. ⑤ 인사말 A/B는 다음 PR이 같은 로그(`variant` 열,
`EventRepository.counts`의 (종류, 변형) 묶음) 위에 얹고, 그때 이 문서에 대안 표를 더한다.

## 고려한 대안

### 1. 무엇을 사건으로 쓰나

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. 다른 표가 모르는 사실만: 서버 사건 `chat_request`(엔진을 부른 요청당 1건, outcome 판별자) + 위젯 사건 `widget_open` (선택) | 지표마다 원천이 하나(TTFT는 `chat_request`, 해결률은 대화·핸드오프 표, 위젯 열림은 `widget_open`), 핸드오프·결제의 주인 표(`Handoff`·`PaymentEvent`·`CreditLedger`)가 그대로 | 자동 해결률은 사건만으로 못 세고 `Conversation`·`Message`·`Handoff` 표를 읽음(지표 계산이 두 원천에 걸침) |
| B. 모든 지표를 사건에서(방문자 핸드오프·결제도 사건으로) | 모든 지표 질의가 `Event` 한 표 | 같은 사실(핸드오프·결제)의 주인이 둘, 턴 저장이 실패해도 답은 정상으로 끝나(`appendTurn` 실패는 보고만) 사건과 대화 표가 갈라짐 |
| C. `chat_turn`·`chat_rejected` 두 종류 | 종류마다 `payload` 모양이 하나라 `outcome` 판별자가 없음, 거절도 종류로 셀 수 있음 | "요청당 1건"이 "두 종류 중 하나"가 됨, 요청 수를 셀 때마다 두 종류를 합쳐야 함 |
| D. 거절(차단 422·크레딧 부족 402)도 `chat_request`로 | 차단(422)·크레딧 부족(402) 거절 수를 사건으로 셈 | 모델을 부르지 않는 비용 0 요청도 행이 됨, 공개 키만으로 행을 쌓음(2026-11-05 검토에서 같은 IP 욕설 300건이 422 300건·행 300개, 당시 `/api/chat` 요율 제한 없음), 지금의 IP당 20/분도 IP 하나의 속도만 누름 |

### 2. 쓰기 경로

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. 통로 하나 `EventSink`(`(event) => void`), 턴 트랜잭션과 분리, 저장 실패는 통로 안에서 `reportError` (선택) | 반환이 `void`라 응답이 분석용 쓰기를 기다리지 않고 호출자가 catch를 잊어 프로세스가 죽는 길이 없음, 성공·실패·중단 턴이 모두 같은 `finish` 한 길 | 사건과 턴 저장이 원자적이지 않음, 쓰기를 기다리지 않아 프로세스가 갑자기 끝나면 아직 저장되지 않은 사건을 잃음 |
| B. `chat_request`를 `appendTurn` 트랜잭션 안에 | 사건과 턴(차감 포함)이 한 트랜잭션이라 함께 남거나 함께 빠짐 | 실패·중단 턴은 `appendTurn`에 닿지 않아 사건을 쓰는 두 번째 길이 생김, TTFT는 HTTP 계층(`http/chat.ts`)이 재므로 유스케이스가 그 값을 받아야 함 |
| C. stdout `chat_usage` 줄을 유지하고 DB와 병행 | 이미 있던 줄이라 바꿀 코드가 적음, DB 저장이 실패해도 프로세스 로그에 남음 | 같은 요청의 기록이 둘이라 어긋나면 어느 쪽이 맞는지 정해야 함, stdout 줄은 프로세스 로그라 따로 모아야 집계됨 |

stdout 줄은 남겼다. 같은 통로가 `NODE_ENV`가 production이 아닐 때 사건 JSON을 한 줄씩 함께 찍는다(개발·verify용, 컨테이너는 끔).

### 3. 위젯 열림을 어디서 세나

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. 대화창 iframe이 처음 열릴 때 `POST /api/events`(페이지 로드당 1건) (선택) | 대화창 JS가 실제로 돌고 방문자가 패널을 연 때만 셈(페이지 로드당 1건) | 공개 키만 알면 Origin 없는 호출로 꾸밀 수 있음, DB에 행을 만드는 공개 쓰기 경로가 하나 늘어 요율 제한(IP당 30/분)·본문 상한(1kb)을 따로 둠 |
| B. `GET /frame` 200을 서버 사건으로 | 위젯 코드가 그대로(서버가 문서 요청을 셈), 꾸미려면 허용 사이트 오리진(`o`)이 필요(다만 그 목록은 `/frame` 응답의 CSP 헤더에 보임) | 허용된 오리진을 `o`로 넣어 다른 사이트에 끼우면 frame-ancestors로 그려지지 않아도 200으로 셈, `/frame`에는 요율 제한이 없음, 상태를 바꾸는 GET이라 미리 가져오기·크롤러 요청도 셈 |

### 5. 지표 정의

| 항목 | 선택 | 버린 것 |
| --- | --- | --- |
| 정의의 자리 | `apps/server/src/events/metrics.ts` 한 곳. 저장소는 사실(값 목록·대화별 사실·개수)만 | 저장소마다 SQL·JS로 따로 |
| TTFT 백분위 | nearest-rank(⌈p·n/100⌉번째) = Postgres `percentile_disc` | `percentile_cont`(보간) |
| TTFT 표본 | 창 안 `chat_request` 중 공백이 아닌 답변 조각을 보낸 요청(`ttftMs` 있음). 공백뿐인 조각은 첫 응답이 아니다(유스케이스도 공백뿐인 답은 답 없음) | 모든 요청, 공백 조각도 첫 응답으로 |
| 해결률 원천 | `Conversation`·`Message`·`Handoff` 표 | 사건 |
| 해결률 분모 | 창 안에 시작해 질문(방문자 메시지)이 있었던 대화. 질문 없이 연결만 요청한 대화는 분모·분자 모두에서 뺀다 | 창 안에 시작한 대화 전부(공개 `/api/handoff`만으로 분모가 부풀었다), 마지막 메시지 뒤 30분 무활동인 대화만 |
| 해결률 분자 | 답 ≥ 1, Handoff 행 0(출처·상태 무관) | 모델 신호만 |
| 창 | 최근 7일 고정 `[now − 7×24h, now)`, 쿼리 파라미터 없음 | 기간 파라미터, 전체 기간 |
| 위젯 열림 | 수만 표시, 서버 사건과 비율을 만들지 않음 | 열림 대비 질문 비율 |

### 7. 인사말 A/B

방문자가 대화창을 처음 열면 인사말 둘 중 하나를 본다. 서버가 방문자마다 배정하고, 같은 방문자는 다시 와도 같은 인사말을 보며,
콘솔 `#/metrics`가 인사말별로 노출 → 첫 질문을 비교한다. 같은 사건 로그의 `variant` 열과 (종류, 변형) 묶음 위에 얹었다. 스키마는 그대로다.

#### 7-1. 서버의 배정이 대화창에 닿는 길

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. 대화창이 처음 뜰 때 같은 오리진 `GET /api/greeting?tenant=&variant=`로 묻는다(사건을 남기지 않음) (선택) | `/frame`(사람 머지 경로)·CSP·verify launch가 그대로, 대화창 문서에 데이터를 심지 않음, 변형 목록·문구는 서버(`GREETING_EXPERIMENT`)에만 | 처음 열 때 요청이 하나 늘어 인사말이 그만큼 늦게 그려짐, 열림 사건이 인사말 요청을 최대 3초 기다림(그 사이 떠나면 열림을 잃음) |
| B. `/frame`이 302로 `v=`를 붙인다 | 인사말 요청이 따로 없음(요청 하나 덜) | 사람이 머지하는 `http/frame.ts`를 고침, verify launch·doctor가 `redirect: 'manual'`로 `/frame` 200을 기대해 깨짐, 런처는 다른 오리진 iframe의 최종 URL을 못 읽어 보존에 메시지가 또 필요 |
| C. 변형 목록을 대화창 번들·contracts에 두고 대화창이 고른다 | 첫 방문에도 인사말 요청이 없음 | "서버가 배정"(§7)과 다름, 사건 검증·콘솔 지표도 같은 목록을 봐야 해서 목록이 둘이 되거나 contracts가 서버 정책을 품음 |
| D. 배정과 노출 기록을 `POST /api/greeting` 한 요청으로 | 노출의 변형을 서버가 배정한 값 그대로 직접 씀 | 내용을 돌려주는 공개 쓰기 엔드포인트가 새로 생겨 요율 제한·위조 대책이 하나 더, 열림을 두 곳(`widget_open`·인사말 POST)에서 셈, 인사말이 그려지기 전에 패널을 닫아도 노출로 셈 |

#### 7-2. 방문자 단위 보존

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. 런처가 고객 사이트 localStorage(`qrate.greeting.<테넌트>`)에 변형 id를 두고 대화창 URL `v=`로 돌려준다. 값은 대화창 → 런처 `greeting` 메시지로 받는다(D1 확장) (선택) | 런처가 도는 고객 사이트의 1자 저장소라 3자 저장소 분할에 걸리지 않음, 값이 변형 id라 같은 변형의 모든 방문자에게 같은 문자열, 값이 맞는지는 서버가 판정(`assignGreeting`) | 대화창이 런처에 `greeting` 메시지를 보내 postMessage 계약(D1)이 넓어짐, 고객 사이트 저장소라 그 사이트의 동의 정책을 따름(웹 저장소도 동의 규정 대상, 영국 ICO), 저장소가 막힌 브라우저는 페이지 로드마다 새로 배정 |
| B. 대화창(서버 오리진)의 자기 localStorage | 런처와 postMessage 계약(D1)이 그대로 | iframe 저장소는 최상위 사이트별로 분할(Chrome 115+, Firefox 103+), Safari는 7일간 상호작용이 없는 사이트의 스크립트 저장소를 지움(iframe 저장소에 적용되는지는 실측 없음) |
| C. 런처가 무작위 버킷(0~99)을 보존하고 서버가 버킷 → 변형을 정한다 | postMessage 계약(D1)이 그대로라 대화창이 런처에 보낼 메시지가 없음 | 방문자마다 다른 영속 무작위 값이라 약한 식별자에 가까움(변형 id는 같은 변형의 모든 방문자에게 같음), 비율을 바꾸거나 변형을 더하면 버킷 경계가 움직여 기존 방문자가 다른 변형으로 옮겨짐 |
| D. 방문자 id(영속 무작위 UUID)를 두고 방문자 단위로 분석한다 | 노출(페이지 로드)이 아니라 방문자 단위로 분석 | 방문자마다 영속 식별자를 남겨 개인정보 처리 결정이 필요 |

#### 7-3. 노출·전환 사건

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. 노출 = 기존 `widget_open`에 화면에 보인 인사말의 변형을 싣는다(인사말 요청이 끝난 뒤 나감), 전환 = 새 종류 `first_question`(페이지 로드당 재시도가 아닌 첫 질문, 서버 결과와 무관) (선택) | 이미 보내는 `widget_open`에 변형을 실어 같은 순간의 사건이 하나, `variant` 열·(종류, 변형) 묶음이 그대로, 노출·전환 모두 브라우저 보고라 분자·분모가 같은 신뢰 수준 | 공개 키만 알면 두 사건을 꾸밀 수 있음, `/api/events`가 페이지 로드당 최대 2건(IP당 30/분 안), 차단·크레딧 부족·요율 제한(422·402·429)으로 막힌 첫 질문도 전환 |
| B. 노출을 새 종류 `greeting_view`로 | `widget_open`이 "열림" 한 뜻으로만 남음 | 같은 순간의 사건이 둘이라 한쪽만 유실되면(닿지 못한 사건은 버림) 어느 쪽을 믿을지 정해야 함, 페이지 로드당 POST가 3건 |

## 결정

### 무엇을 사건으로 남기나

다른 표에 이미 기입된 데이터는 이벤트 로그에 기록하지 않기로 결정. 지표마다 각 정보의 원천을 하나만 둔 것임.
또한 답변 모델을 호출하지 않은 요청도 DB에 기록해놓는것은 서버 리소스 낭비이기에 실제 호출 요청만 기록하도록 변경했고.
공개 키는 고객 사이트에 그대로 보이는 값이라, 누구에게나 기록을 늘릴 수 있는 위험이 존재.

### 사건을 쓰는 길

방문자에게 답을 보내는 일이 사건 저장을 기다리지 않는다. 메시지를 보냈다는 사건 저장에 실패해도 답은 정상적으로 간다는 의미.
사건 저장과 대화 저장은 별개로 운영된다. 사건은 존재하지만 대화가 존재하지 않는 케이스가 있기에 둘을 묶어서 처리하지 않음. 물론 영향은 개별로 받지만.

### 위젯 열림을 세는 곳

위젯 열림은 대화창(iframe)이 열림을 알린다.
대화 내용은 고객 사이트가 들여다볼 수 없는 독립된 창에서 오가고 런처는 서버와 직접 이야기하지 않기에, 런처가 열렸다는 쪽지를 대화창에 주면 대화창이 서버에 알린다.
실제 대화창이 열린 경우에 한해 열림 횟수를 센다.

(본인 작성 — 남은 것: 지표 정의는 한 곳(nearest-rank, 해결률은 대화·핸드오프 표, 분모는 창 안에 시작해 질문이 있었던 대화, 7일 고정),
스키마는 문자열 `type`·`ttftMs` 열·테넌트 FK, 콘솔은 새 라우트. 왜 보간하지 않는지를 직접 쓸 것. 프로젝트를 더 진행한 뒤 작성.)

### 인사말 A/B

고객 사이트의 방문자에게 동일한 인사말을 보이기 위해 localStorage에 인사말 관련 데이터를 캐싱해둔다.
서버의 배정은 대화창에서 서버에 직접 요청을 보내는 것으로 진행.
서버가 대화창 주소에 배정을 실어 보내는 방법(302)도 있었지만, 런처는 대화창의 주소를 읽지 못해 어차피 추가 메시지가 필요했고 수정할 모듈만 늘어 버렸다.
노출은 인사말이 보인 페이지의 첫 열림, 전환은 그 페이지의 첫 질문으로 세고, 단위는 페이지를 연 번마다이며 막힌 질문도 센다.
전환율은 열림과 첫 질문 둘 다 방문자 브라우저가 보고한 수라 같은 신뢰 수준끼리의 비율이므로, 위젯 사건과 서버 사건을 섞지 않는다는 원칙과 어긋나지 않는다. 대신 둘 다 꾸밀 수 있어 방문자 브라우저 보고 출처를 붙여 보여준다.

## 트레이드오프

### 무엇을 사건으로 남기나

- 거절된 요청의 수는 현재 셀 수 없는데, 기록에 포함되지 않기에 거절된 요청 수를 세는 카운터를 별도로 개발해야돼.
- 자동 해결률은 이벤트 로그만으로 셀 수 없다. 그렇기에 상담원 연결 요청이 있었는지 대화·핸드오프 표를 함께 참조해야 한다는 것이 단점이다. 이건 고도화시키며 고민해봐야함.

### 사건을 쓰는 길·위젯 열림

- 서버가 갑작스럽게 다운되면 사건이 저장되지 않을 수 있음.
- 위젯 열림 사건은 공개된 주소로 보내기에 누구나 꾸며 보낼 수 있다. 같은 오리진 검사·IP당 분당 30회·허용된 종류만 받기로 줄일 뿐이라, 콘솔은 이 수를 방문자 브라우저가 보고한 수로만 보여 준다.

### 인사말 A/B

- 브라우저 상황에 따라 동일 유저가 다른 인사말을 볼 수 있다는 것.
- 대화창이 열릴 때 서버에 전달되는 요청이 추가된다는 것. 열림 기록이 인사말을 최대 3초 기다리는 동안, 유저가 떠난다면 열림 기록은 DB에 저장되지 않음.
