# ADR-0008: 이벤트 로그 — 사건 등록표, 쓰기 통로, 콘솔 지표 정의

- 상태: proposed → 본인이 결정 이유·트레이드오프를 채운 뒤 accepted로 변경할 것
- 날짜: 2026-11-05
- 작성: 강지원

## 맥락

정의서의 성공 지표 중 둘이 이 PR의 대상이다. TTFT p50·p95는 "이벤트 로그 집계", 자동 해결률은 "핸드오프 없이 종료된 대화 비율(시나리오 기준 명시)"이다.
지금까지 TTFT는 `/api/chat` 요청마다 stdout에 찍히는 `chat_usage` JSON 한 줄에만 있었다. 그 줄은 프로세스 로그라 집계할 곳이 없고,
README에 적을 수치를 "어느 행에서 나왔는가"까지 따라갈 방법이 없었다. `Event` 표는 init 마이그레이션에 있었지만 어떤 코드도 쓰지 않았다.

사실의 주인은 이미 갈라져 있다. 핸드오프는 `Handoff` 표(모델 신호·방문자 요청 두 출처), 결제는 `PaymentEvent`·`CreditLedger`가 갖고 있다.
TTFT·실패·거절·위젯 열림만 어디에도 없었다. 실패·중단된 턴은 `appendTurn`에 닿지 않아 대화 표에 남지 않고, TTFT는 HTTP 계층만 안다.
저장소 구현이 둘(메모리·Postgres)이라 백분위 정의가 두 구현에서 같아야 한다. 위젯의 런처는 서버를 부르지 않으므로(ADR-0003) 열림을 아는 곳은
서버 오리진의 대화창 iframe뿐이고, 거기서 오는 공개 POST는 공개 키만 있으면 꾸밀 수 있다.

W4 결정(2026-11-05) 다섯 가지 중 ①~③은 ADR-0007이다. 이 ADR은 ④ 이벤트 로그를 다룬다. ⑤ 인사말 A/B는 다음 PR이 같은 로그(`variant` 열,
`EventRepository.counts`의 (종류, 변형) 묶음) 위에 얹고, 그때 이 문서에 대안 표를 더한다.

## 고려한 대안

### 1. 무엇을 사건으로 쓰나

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. 다른 표가 모르는 사실만: 서버 사건 `chat_request`(테넌트를 찾은 요청당 1건, outcome 판별자) + 위젯 사건 `widget_open` (선택) | (채워 넣기 — 힌트: 지표마다 원천이 하나, 핸드오프·결제의 주인이 그대로) | (채워 넣기 — 힌트: 해결률은 사건만으로 못 셈, 두 표를 읽음) |
| B. 모든 지표를 사건에서(방문자 핸드오프·결제도 사건으로) | (채워 넣기 — 힌트: 질의가 한 표) | (채워 넣기 — 힌트: 같은 사실의 주인이 둘, 턴 저장이 실패하면 두 원천이 갈라짐) |
| C. `chat_turn`·`chat_rejected` 두 종류 | (채워 넣기) | (채워 넣기 — 힌트: "요청당 1건"이 "둘 중 하나"가 됨, ④의 전환율이 두 종류를 합쳐야 함) |

### 2. 쓰기 경로

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. 통로 하나 `EventSink`(`(event) => void`), 턴 트랜잭션과 분리, 저장 실패는 통로 안에서 `reportError` (선택) | (채워 넣기 — 힌트: 응답이 분석용 쓰기를 기다리지 않음, 실패·중단 턴도 같은 길, 호출자가 catch를 잊을 수 없음) | (채워 넣기 — 힌트: 사건과 턴 저장이 원자적이지 않음, 프로세스 종료 시 미저장 사건 유실) |
| B. `chat_request`를 `appendTurn` 트랜잭션 안에 | (채워 넣기 — 힌트: 원자적) | (채워 넣기 — 힌트: 실패·중단 턴은 거기 닿지 않아 두 번째 경로가 생김, 유스케이스가 TTFT를 알아야 함) |
| C. stdout `chat_usage` 줄을 유지하고 DB와 병행 | (채워 넣기) | (채워 넣기 — 힌트: 기록이 둘, 어느 쪽이 맞는지 정해야 함) |

stdout 줄은 남겼다. 같은 통로가 `NODE_ENV`가 production이 아닐 때 사건 JSON을 한 줄씩 함께 찍는다(개발·verify용, 컨테이너는 끔).

### 3. 위젯 열림을 어디서 세나

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. 대화창 iframe이 처음 열릴 때 `POST /api/events`(페이지 로드당 1건) (선택) | (채워 넣기 — 힌트: JS가 실제로 돌고 방문자가 연 상태일 때만) | (채워 넣기 — 힌트: 공개 키로 위조 가능, 공개 쓰기 경로가 하나 늘어남) |
| B. `GET /frame` 200을 서버 사건으로 | (채워 넣기 — 힌트: 위조가 조금 어렵고 위젯 코드가 그대로) | (채워 넣기 — 힌트: frame-ancestors로 그려지지 않은 창도 셈, /frame에 요율 제한 없음, 부수 효과 있는 GET) |

### 4. 스키마

| 항목 | 선택 | 버린 것 |
| --- | --- | --- |
| `type` | 문자열(종류의 등록표는 코드의 `AppEvent` 유니온) | Prisma enum |
| TTFT | `ttftMs` 열 | `payload` JSON 안 |
| `tenantId` | NOT NULL + FK, 인덱스 `(tenantId, type, createdAt)` | nullable, `(type, createdAt)` |
| `conversationId` | 열, FK 없음(실패·중단 턴의 대화는 저장되지 않는다) | FK |
| `payload` | NOT NULL Json, 자유 문자열 필드 없음(질문·답 원문이 들어갈 자리가 없다) | 요청 본문 일부 저장 |

### 5. 지표 정의

| 항목 | 선택 | 버린 것 |
| --- | --- | --- |
| 정의의 자리 | `apps/server/src/events/metrics.ts` 한 곳. 저장소는 사실(값 목록·대화별 사실·개수)만 | 저장소마다 SQL·JS로 따로 |
| TTFT 백분위 | nearest-rank(⌈p·n/100⌉번째) = Postgres `percentile_disc` | `percentile_cont`(보간) |
| TTFT 표본 | 창 안 `chat_request` 중 첫 답변 조각을 보낸 요청(`ttftMs` 있음) | 모든 요청 |
| 해결률 원천 | `Conversation`·`Message`·`Handoff` 표 | 사건 |
| 해결률 분모 | 창 안에 시작한 대화 전부(질문 없이 연결만 요청한 대화 포함) | 마지막 메시지 뒤 30분 무활동인 대화만 |
| 해결률 분자 | 답 ≥ 1, Handoff 행 0(출처·상태 무관) | 모델 신호만 |
| 창 | 최근 7일 고정 `[now − 7×24h, now)`, 쿼리 파라미터 없음 | 기간 파라미터, 전체 기간 |
| 위젯 열림 | 수만 표시, 서버 사건과 비율을 만들지 않음 | 열림 대비 질문 비율 |

| --- | --- | --- |

| B. 미응답 큐·대화 로그 화면에 카드 | (채워 넣기) | (채워 넣기 — 힌트: 큐는 운영자의 작업 목록) |

## 결정

(본인 작성 — 2026-11-05에 고른 것: 사건은 다른 표가 모르는 사실만(`chat_request`·`widget_open`), 쓰기는 턴 트랜잭션과 분리한 통로 하나,
위젯 열림은 대화창이 보냄, 스키마는 문자열 `type`·`ttftMs` 열·테넌트 FK, 지표 정의는 한 곳(nearest-rank, 해결률은 대화·핸드오프 표,
분모는 창 안에 시작한 대화 전부, 7일 고정), 콘솔은 새 라우트. 왜 원자성보다 분리를 골랐는지, 왜 보간하지 않는지, 해결률 "종료"를
30분 무활동이 아니라 창 안의 대화 전부로 둔 것이 "시나리오 기준 명시"와 어떻게 맞는지를 직접 쓸 것.)

## 스스로 답해볼 유도 질문

1. 사건 쓰기를 턴 트랜잭션과 묶지 않았다. 사건은 남았는데 턴 저장이 실패하면(또는 그 반대) 어느 지표가 어떻게 흔들리나? 지표마다 원천이 하나라는 것이 그 흔들림을 어디까지 막나?
2. `EventSink`가 `void`를 돌려주는 것이 호출자에게 무엇을 금지하나? `finish()`가 await되지 않는 지금 구조에서 저장 실패가 프로세스를 죽이는 길은 어떻게 막혔나?
3. 표본이 2건이면 p95는 무엇인가? `percentile_cont`였다면 README의 p95를 어느 행까지 따라갈 수 있나?
4. 해결률 분모에 "질문 없이 연결만 요청한 대화"를 넣었다. 빼면 비율이 어느 쪽으로 움직이고, 정의서 문장에는 어느 쪽이 가까운가? 30분 무활동 정의였다면 데모·verify에서 무엇이 달라지나?
5. `widget_open`은 공개 키로 위조할 수 있다. 같은 오리진 검사·IP 요율 제한·종류 화이트리스트가 각각 막는 것과 못 막는 것은? 콘솔이 비율을 만들지 않는 이유는?
6. `type`을 enum이 아니라 문자열로 둔 이유를 "새 종류를 쓴 뒤 코드를 되돌리는" 롤백으로 설명할 수 있나?
7. `ttftMs`를 `payload`에 두었다면 백분위 질의와 인덱스는 어떻게 달라지나?
8. stdout 사건 줄을 production에서 끈 이유는? 운영에서 사건을 보는 길은 무엇이 남나?
9. 프록시 뒤에서 `trust proxy`가 없으면 `/api/events`의 IP 요율 제한은 무엇을 세게 되나?

## 결과 확인 방법

- 사건 기록: 테넌트를 찾은 `/api/chat` 요청당 정확히 1건(400·403·404·500은 0건), 직렬화한 사건에 질문·답 원문 없음, 사건 저장이 실패해도
  응답은 `[DONE]`으로 끝나고 보고는 한 번(`apps/server/test/chat.test.ts`).
- 위젯 사건 수집: 202·빈 payload·테넌트 id, `chat_request`·모르는 종류 400 `invalid_event`, 403·404·413·429, 요율 카운터는 상담원 연결과 따로
  (`apps/server/test/events-api.test.ts`). 대화창 전송(`packages/widget/test/events.test.ts`)과 위젯 E2E(열면 1건, 닫았다 다시 열어도 1건).
- 저장소 계약(메모리·Postgres): 창 `[from, to)`·테넌트 경계의 TTFT 표본과 (종류, 변형) 개수, 대화별 `{ answered, handedOff }`(`repo-contract.ts`).
- 지표 정의: n = 0·1·2·20·37·100, 섞인 입력·동률·숫자 정렬, 해결 경계, 창 전달(`apps/server/test/metrics.test.ts`).
  Postgres에서 같은 행에 대한 `percentile_disc(ARRAY[0.5, 0.95])`가 콘솔 값과 같음(`repo-postgres.test.ts`).
- 콘솔: `GET /api/console/metrics` 빈 상태·집계(`console-api.test.ts`), 지표 화면 E2E(`apps/console/e2e/console.spec.ts`),
  verify 여정 `metrics`(화면 값 = API 값 = server.log의 `chat_request` ttftMs).
