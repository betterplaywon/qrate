# ADR-0005: 핸드오프 신호 — 모델의 "자료에 없다" 판단을 도구 호출로 받는다

- 상태: proposed → 본인이 결정 이유·트레이드오프를 채운 뒤 accepted로 변경할 것
- 날짜: 2026-11-03
- 작성: 강지원

## 맥락

시스템 지시에는 "자료에 없는 내용은 모른다고 말하고 상담원에게 문의하도록 안내한다"는 원칙이 있고, 모델은 대체로 그렇게 답한다.
문제는 그 답이 글자일 뿐이라는 점이다. 사용량 로그에는 `outcome: done`으로만 남아 자료로 답한 턴과 모른다고 답한 턴이 구분되지 않고,
성공 지표 "자동 해결률(핸드오프 없이 종료된 대화 비율)"의 분자를 셀 수 없다. W3 미응답 큐에 무엇을 넣을지, W5 평가셋의 핵심 케이스
"문서에 없는 질문 → 모른다 + 상담원 연결"을 어떻게 채점할지도 이 신호에 달려 있다.

핸드오프는 두 종류다. 방문자가 누르는 "상담원 연결" 버튼(항상 보임, 실제 연결은 W3)과, 모델이 내는 신호. 이 ADR은 후자의 **출처**를 정한다.
신호가 흘러가는 길은 어느 선택에서나 같다: 엔진 이벤트 → SSE `event: handoff {reason, summary?}` → 대화창의 연결 제안 안내, 사용량 로그 `handoff` 필드(W4 이벤트 로그), W3 큐, W5 채점.

## 고려한 대안

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. 텍스트 마커 — 답 끝에 약속한 글자를 쓰게 하고 서버가 찾아 지움 | 프롬프트 한 줄과 서버의 글자 찾기로 끝남, 도구 정의가 없어 접두사가 늘지 않음(도구를 넣자 7,399에서 8,146토큰), 모델·제공자의 도구 기능과 무관 | 마커가 조금만 바뀌어도 놓치고 놓친 수를 셀 수 없음(못 찾은 마커는 방문자에게 그대로 보임), 조각 경계에 걸친 마커를 붙잡아 둘 버퍼가 필요(본문 도구 태그를 거르는 `ToolMarkupFilter`가 같은 일), 방문자가 마커를 쓰게 유도해 위조 가능·사유 필드 없음 |
| B. 도구 호출 (선택) — 신호용 도구 `request_handoff{reason, summary}`, 호출 자체가 신호 | 신호가 응답의 별도 `tool_use` 블록이라 글자 비교가 없고 방문자 글로 만들 수 없음, 사유(enum)·요약을 `input_schema`로 받고 놓침은 호출 부재로 셈, 호출이 답 글 뒤에 와 첫 글자를 늦추지 않음(시드 실측 2, 텍스트 블록 4개 뒤 `tool_use`) | 모델이 안내 문장 없이 도구만 부르거나(도구 설명으로 금지, W5 2회차 0건) 호출을 본문 글자로 씀(W5 1회차 Sonnet 1/60, `ToolMarkupFilter`로 막음), 과잉·과소 호출을 따로 재야 함(W5 2회차 Sonnet 놓침 0/18·과잉 0/36, Haiku 과잉 2/36), 도구를 넣자 캐시 접두사가 7,399에서 8,146토큰으로 늘고(도구 정의·API의 도구 사용 안내문·지시 한 줄) Sonnet 5.5는 사고 설정과 무관하게 도구 강제 호출(`tool_choice` any·tool)이 400이라 auto로만 부름 |
| C. 사후 판정 — 답이 끝난 뒤 작은 모델이 "모른다고 답했는가" 판정 | 답변 프롬프트·도구와 분리돼 답에 영향이 없음, 저장한 답에 오프라인으로 다시 돌릴 수 있음(W5 심판 Opus 5.5가 이 방식) | 턴마다 모델 호출이 2회, 답이 끝난 뒤에야 신호가 나 연결 제안이 늦음, 판정 정확도를 다시 재야 함(W5는 사람 채점과 대조해 알맞음 일치 27/30) |
| D. 구조화 출력 — `{answer, handoff}` JSON | 제약 디코딩으로 스키마에 맞는 JSON만 나와 `handoff` 필드가 빠지지 않음, 신호와 답이 한 응답에 함께 옴 | 답이 JSON 문자열 안에 있어 조각을 그대로 `delta`로 못 보냄(서버가 부분 JSON을 풀거나 SSE 계약을 바꿈), 인용(citations)과 함께 쓰면 400(공식 문서) |

## 스스로 답해볼 유도 질문

1. 신호가 틀릴 때 더 나쁜 쪽은 놓침(운영자가 모르는 미응답)인가 오탐(불필요한 연결 제안)인가? 그 판단이 A와 B의 선택을 어떻게 가르는가?
2. "도구를 실행하지 않는 도구"가 왜 성립하는가? 도구 호출의 본래 흐름(tool_result를 돌려주고 이어서 답함)과 무엇이 다른가?
3. 도구 정의는 프롬프트 접두사의 맨 앞(tools → system → messages)에 들어간다. 이것이 프롬프트 캐시에 미치는 영향은 무엇이고, 도구 설명을 자주 고치면 어떻게 되나?
4. 사용자가 "상담원 연결해 주세요"라고 입력하면 모델이 도구를 부를 수 있다. 이것은 위조인가, 바른 동작인가? A의 마커 위조와 어떻게 다른가?
5. W5에서 C(사후 판정)를 심판으로 써서 B의 놓침을 잰다면, 심판 자체의 정확도는 무엇으로 보증하나?
6. 인용 0건은 왜 신호가 아니라 보조 지표인가?

## 결과 확인 방법

- 목업 훅 `[[handoff]]`로 계약을 고정한다: 안내 조각 → `event: handoff` → `done`, 인용 없음, 사용량 로그 `handoff`·`citations`(`apps/server/test/chat.test.ts`, `packages/widget/test/stream.test.ts`, E2E).
- 실제 호출 2회(2026-11-03): 시드 노트의 비워 둔 주제 질문에는 안내 문장 뒤 `request_handoff` 호출이, 자료에 있는 질문에는 인용만 나와야 한다. 결과는 `apps/server/seed/demo-tenant.notes.md` 실측 절에 기록한다.
- W5 평가셋: 비워 둔 주제 9개 질문의 신호 유무와 자료에 있는 질문의 오탐을 센다. 자동 해결률은 사용량 로그의 `handoff`로 계산한다.
