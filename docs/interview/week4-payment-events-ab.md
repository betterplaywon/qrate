# W4 면접 질문 뱅크 — 결제 멱등 · 이벤트 로그 · 요율 제한 · 인사말 A/B

사용법은 [W1](week1-infra.md)과 같다: 코드를 보지 않고 답한다 → 답을 적어 Claude 세션에 첨부하고 **"채점해줘"** → 막힌 것은 코드를 읽고 다시 답한다 → 잘 답한 것 하나를 블로그로 옮긴다.

W4 결정은 ADR-0007(크레딧·결제 멱등)과 ADR-0008(이벤트 로그·인사말 A/B)에 있다. ADR의 "스스로 답해볼 유도 질문"은 여기서 반복하지 않는다 — ADR에 답을 쓴 뒤 말로 재연습한다.

---

## 결제 멱등

1. 멱등 키의 유일 제약을 전역이 아니라 `(tenantId, idempotencyKey)`로 잡았다. 키를 클라이언트(콘솔)가 만드는 구조에서 전역 유일이었다면 다른 테넌트가 무엇을 할 수 있었나?
2. 충전 요청을 같은 `Idempotency-Key`로 다시 보내면 201과 처음 만든 직후의 주문, `Idempotent-Replayed` 헤더를 돌려준다. 처음 구현은 지금 상태(결제 완료)를 돌려줬다. 그것이 왜 "중복은 같은 응답" 결정을 어겼나? 같은 키에 다른 본문이면 왜 422인가?
3. 웹훅은 서명을 원문(raw body) 위에서 확인한 뒤에야 JSON으로 읽는다. 먼저 파싱하면 서명 검증이 어떻게 틀어질 수 있나? 서명에 시각을 넣고 300초 창을 둔 것은 무엇을 막나?
4. 충전 주문의 상태는 pending < failed < paid 순서로만 움직이고 failed → paid는 허용한다. 같은 이벤트 집합이면 배달 순서와 상관없이 끝 상태가 같은 이유를 "최댓값"으로 설명하라. failed를 끝 상태로 두면 고객에게 무슨 일이 생기나?
5. `PaymentEvent`는 `(provider, eventId)`를 키로 처음 판정을 저장하고, 같은 이벤트가 다시 오면 그 판정을 그대로 돌려준다. 다시 계산하지 않는 이유는? 저장소가 이벤트 차지 → 상태 CAS → 원장 순서로 일하는 이유는?
6. 결제 제공자 기본값을 "`NODE_ENV`가 development·test일 때만 모의 결제"로 닫았다. `NODE_ENV`가 없을 때 모의 결제가 열려 있었다면 운영 서버에서 누가 무엇을 할 수 있었나?

## 이벤트 로그 · 지표

7. 위젯 사건은 `fetch(…, { keepalive: true })`로 보낸다. `navigator.sendBeacon`에 문자열을 넘기면 서버의 `express.json`이 왜 읽지 못하나? keepalive가 없으면 열자마자 페이지를 떠날 때 무엇을 잃나?
8. 메모리와 Postgres 저장소가 같은 TTFT 백분위를 낸다는 것을 테스트는 어떻게 증명하나? 정의를 두 번 구현하지 않고 저장소는 값 목록만 돌려주게 한 것이 그 증명을 어떻게 쉽게 했나?
9. 위젯 E2E는 서버 하나가 모든 테스트의 사건을 한 IP(루프백)에서 받는다. 사건을 보내는 테스트가 늘어 `/api/events`의 IP당 30회/분 한도에 닿으면 어떤 단언이 어떤 메시지로 깨질까? 테스트를 위해 한도를 여는 옵션을 두지 않은 이유는?

## 요율 제한

10. 대화 API 요율 제한을 Origin 검사 뒤, 본문 파싱 앞에 붙였다. 순서를 Origin 앞으로 옮기면, 또 본문 파싱 뒤로 옮기면 각각 무엇이 달라지나?
11. 요율 제한 라이브러리는 IPv6를 주소 하나가 아니라 /56 대역 하나로 센다. /64로 좁히면 무엇이 쉬워지고 무엇이 나아지나? 이동통신망처럼 기기마다 /64를 주는 곳에서는 무슨 일이 생기나?
12. 리버스 프록시 뒤에 `trust proxy` 없이 배포하면 요율 제한은 무엇을 IP로 보고 세게 되나? `trust proxy`를 무조건 켜면 이번에는 무엇이 가능해지나(`X-Forwarded-For` 위조)?

## 인사말 A/B

13. 대화창 문서(`/frame`)에는 데이터를 심지 않는다. 배정을 문서에 넣을 수 없는 이유를 CSP와 연결해 말하라. `/frame`이 302로 `v=`를 붙이는 안은 왜 "런처가 보존한다"는 문제를 풀지 못했나?
14. 보존 자리를 대화창(서버 오리진 iframe)의 localStorage가 아니라 고객 사이트의 localStorage로 골랐다. 브라우저가 다른 사이트 안에 박힌 iframe의 저장소를 어떻게 다루길래 그런가? 그 대가로 고객 사이트 쪽에 생기는 책임(저장소 동의 정책)은?
15. 배정이 무작위인데 E2E와 verify 여정은 어떻게 결정적인가? "어느 변형이 나오는가" 대신 무엇을 단언했고, 특정 변형이 필요할 때 테스트 전용 엔드포인트 없이 어떻게 만들었나?
16. 적대적 검토가 "인사말이 오기 전에 패널을 닫으면 보지 않은 인사말이 노출로 잡힌다"를 재현했다. 첫 수정(다음 열림까지 미루기)은 무엇을 새로 깨뜨렸고, 그 결함을 테스트가 아니라 무엇이 잡았나? 두 번째 수정은 어느 지표의 뜻을 지켰나?
